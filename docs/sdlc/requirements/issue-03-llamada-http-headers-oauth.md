# Requirements: [F0] Llamada HTTP con headers OAuth correctos

## Source
GitHub Issue #3 — "[F0] Llamada HTTP con headers OAuth correctos" (milestone "F0 — Núcleo de validación", label `enhancement`), repo `claude-usage-widget`.

## US-1: Obtener el estado de uso/rate-limit real de la cuenta llamando a la API de Anthropic con los headers OAuth correctos

**As a** desarrollador del proyecto,
**I want** un `AnthropicApiUsageDataSource` (Infrastructure) que implemente un puerto `IUsageDataSource` (Application) y llame a la API de Anthropic usando el token obtenido de `ITokenProvider` con los headers OAuth correctos,
**so that** el resto de la aplicación pueda obtener la respuesta real de uso/rate-limit de la cuenta sin conocer los detalles de la llamada HTTP.

### Acceptance Criteria

- **GIVEN** el proyecto Application, **WHEN** se inspecciona sus dependencias, **THEN** existe una interfaz `IUsageDataSource` definida en Application (junto a `ITokenProvider`, sin consolidarse en un `IUsageService` monolítico) que no referencia ningún tipo de Infrastructure ni de librerías HTTP concretas, y cuyo método de lectura devuelve un tipo de dominio explícito (p. ej. `UsageSnapshot`, ver Technical Notes) en lugar de un `HttpResponseMessage`, un `string?` o un `Result<T>` genérico.

- **GIVEN** un `AnthropicApiUsageDataSource` construido con una implementación de `ITokenProvider` que devuelve un `TokenResult` de éxito, **WHEN** se invoca el método de obtención de uso, **THEN** la clase primero obtiene el token vía `ITokenProvider.GetTokenAsync` y a continuación construye una petición `POST https://api.anthropic.com/v1/messages` con un payload mínimo (`max_tokens: 1` y un único mensaje trivial), incluyendo los headers `Authorization: Bearer <token>`, `anthropic-version: 2023-06-01`, `anthropic-beta: oauth-2025-04-20`, `User-Agent: claude-code/<versión>` y `Content-Type: application/json` (ver Technical Notes y Dependencies para el detalle y las fuentes de cada uno).

- **GIVEN** un `AnthropicApiUsageDataSource` construido con una implementación de `ITokenProvider` que devuelve un `TokenResult` en cualquier estado de fallo (fichero no encontrado, JSON inválido, token ausente/vacío), **WHEN** se invoca el método de obtención de uso, **THEN** la clase **no** realiza ninguna llamada HTTP y devuelve un `UsageSnapshot` en un estado explícito de fallo distinguible (p. ej. "sin token disponible"), sin lanzar excepciones.

- **GIVEN** que la API de Anthropic responde con código 200 y con las cabeceras `anthropic-ratelimit-unified-5h-*` (ventana de sesión) y `anthropic-ratelimit-unified-7d-*` (ventana semanal) — concretamente `-status`, `-utilization`/`-remaining` y `-reset` (RFC 3339) para cada ventana —, **WHEN** `AnthropicApiUsageDataSource` procesa la respuesta, **THEN** devuelve un `UsageSnapshot` en estado de éxito que expone esas cabeceras "en crudo" (sin calcular countdowns, minutos restantes ni porcentajes — ese cálculo queda fuera de alcance de este issue y corresponde a una clase separada, según la regla de separación de responsabilidades del proyecto). El Acceptance Criteria original del issue ("se valida manualmente que la API responde 200 con headers `anthropic-ratelimit-*`") se interpreta como la validación manual de estos headers `unified-*`; dado que no son documentación oficial de Anthropic (ver Technical Notes), esta validación manual sigue siendo obligatoria antes de dar el issue por completado, y el nombre/formato exacto observado prevalece sobre lo aquí documentado si difiere.

- **GIVEN** que la API de Anthropic responde con código 401 o 403 (token inválido, caducado o rechazado), **WHEN** `AnthropicApiUsageDataSource` procesa la respuesta, **THEN** devuelve un `UsageSnapshot` en un estado explícito de "no autorizado" (nunca lanza una excepción no controlada) y en ningún caso intenta refrescar el token OAuth por su cuenta — el refresco de token nunca se implementa en este proyecto; el consumidor final es responsable de mostrar un aviso claro al usuario.

- **GIVEN** que la llamada HTTP falla por un motivo distinto a 401/403 (error de red, timeout, código 5xx, o una respuesta 200 que no incluye las cabeceras `anthropic-ratelimit-unified-5h-*`/`anthropic-ratelimit-unified-7d-*` esperadas), **WHEN** `AnthropicApiUsageDataSource` procesa el resultado, **THEN** devuelve un `UsageSnapshot` en un estado explícito de fallo distinguible del "no autorizado" (p. ej. "fallo de la petición" / "respuesta inesperada"), nunca lanza una excepción no controlada, y en esta fase (F0) no reintenta la llamada — el retry con backoff es alcance de F2, fuera de este issue.

- **GIVEN** el `AnthropicApiUsageDataSource` implementado, **WHEN** se revisa su responsabilidad, **THEN** la clase únicamente construye la petición HTTP, la envía y traduce la respuesta cruda (código de estado + cabeceras `anthropic-ratelimit-unified-5h-*`/`anthropic-ratelimit-unified-7d-*`) a un `UsageSnapshot` — no calcula countdowns ni porcentajes de rate limit, ni lee el token directamente de ningún fichero (eso sigue siendo responsabilidad exclusiva de `ITokenProvider`), preservando que leer el token, llamar a la API, calcular el countdown y renderizar sean clases distintas.

- **GIVEN** el conjunto de pruebas del proyecto, **WHEN** se ejecuta el test unitario de `AnthropicApiUsageDataSource`, **THEN** dicho test utiliza un `HttpMessageHandler` fake/stub (o `HttpClient` inyectado con un handler simulado) que devuelve respuestas grabadas/sintéticas, y en ningún caso realiza una llamada de red real ni usa un token real, cubriendo como mínimo: éxito 200 con las cabeceras `anthropic-ratelimit-unified-5h-*` y `anthropic-ratelimit-unified-7d-*` presentes, 401/403, y un fallo distinto (p. ej. 500 o cabeceras ausentes en una respuesta 200). Además, un test verifica que la petición saliente incluye los cinco headers de la lista confirmada en Technical Notes (en particular `User-Agent`, dado su impacto directo en el bucket de rate-limit aplicado).

- **GIVEN** un `IUsageDataSource` simulado (p. ej. un futuro `SimulatedUsageDataSource` o el propio `AnthropicApiUsageDataSource`), **WHEN** ambos representan el caso "sin datos"/error, **THEN** lo hacen de la misma manera (mismo tipo `UsageSnapshot`, mismos estados explícitos) en vez de lanzar excepciones, de forma que sean sustituibles entre sí (regla de sustituibilidad tipo Liskov ya aplicada a `ITokenProvider`/`TokenResult`).

## Technical Notes
- **Endpoint y payload (confirmado):** `POST https://api.anthropic.com/v1/messages`, con un payload mínimo (`max_tokens: 1`, un único mensaje trivial) — es el único endpoint que devuelve las cabeceras de rate limit; `POST /v1/messages/count_tokens` **no** sirve para este propósito porque no las devuelve. Esta llamada consume una cantidad mínima de cuota real (1 token de salida) — no existe un endpoint de "solo estado" separado que no consuma cuota. Esto es un trade-off aceptado, no un pendiente (ver Risks).
- **Headers de petición requeridos (confirmado):**
  - `Authorization: Bearer <access_token>` (token obtenido de `ITokenProvider`)
  - `anthropic-version: 2023-06-01`
  - `anthropic-beta: oauth-2025-04-20`
  - `User-Agent: claude-code/<versión>` — **obligatorio**: sin este header la petición cae en un bucket de rate-limit mucho más agresivo (429 persistentes); con él, se aplica el límite normal de una cuenta Max/suscripción. Su ausencia no provoca un fallo funcional inmediato sino una degradación silenciosa del comportamiento, por lo que su presencia debe quedar cubierta por un test explícito (ver Acceptance Criteria).
  - `Content-Type: application/json`
- **Headers de respuesta a exponer en `UsageSnapshot`, en crudo (confirmado):** `anthropic-ratelimit-unified-5h-status`, `anthropic-ratelimit-unified-5h-utilization` / `anthropic-ratelimit-unified-5h-remaining`, `anthropic-ratelimit-unified-5h-reset` (RFC 3339) para la ventana de sesión (5h); y los mismos tres sufijos bajo `anthropic-ratelimit-unified-7d-*` para la ventana semanal (7d).
- **Referencia externa, no documentación oficial de Anthropic:** los headers `anthropic-ratelimit-unified-*` (5h = sesión, 7d = semana) son específicos del flujo OAuth de cuentas de suscripción (Claude Max/Code) y **no figuran en la documentación pública oficial** de Anthropic (`platform.claude.com/docs/en/api/rate-limits`, que solo documenta `anthropic-ratelimit-requests-*`/`anthropic-ratelimit-tokens-*`/`anthropic-ratelimit-input-tokens-*`/`anthropic-ratelimit-output-tokens-*` para claves de API de pago por uso — headers que probablemente no aparezcan, o sean irrelevantes, en el flujo OAuth de Claude Code). El endpoint, payload, headers de petición y headers de respuesta anteriores se conocen por ingeniería inversa de la comunidad, contrastada contra: CodexBar issue #1894, openclaw issue #56047, y claude-code issue #55333. Al no ser un contrato oficial, puede cambiar sin aviso — de ahí que el propio Acceptance Criteria del issue original ("validar manualmente que la API responde 200 con headers `anthropic-ratelimit-*`") siga siendo obligatorio antes de cerrar el issue, y que el resultado observado en esa validación manual prevalezca sobre lo aquí documentado si hay discrepancias.
- **Tipo del resultado (`UsageSnapshot`):** el "resultado sin datos"/error debe modelarse como un tipo de dominio dedicado, análogo a `TokenResult` (enum de estado explícito + factory methods estáticos + ctor privado), viviendo en **Domain** (p. ej. `ClaudeMeter.Domain.Usage.UsageSnapshot`), ya que `IUsageDataSource` en Application solo puede depender de Domain. Estados mínimos sugeridos: éxito (con las cabeceras `anthropic-ratelimit-unified-5h-*`/`anthropic-ratelimit-unified-7d-*` en crudo), sin token disponible, no autorizado (401/403), fallo de la petición/respuesta inesperada.
- Este issue **no** incluye el parseo de las cabeceras `anthropic-ratelimit-unified-*` a minutos/porcentaje ni la construcción de `RateLimitWindow` — esa responsabilidad, mencionada en el roadmap F0 ("parse anthropic-ratelimit-* headers into minutes/percentage"), corresponde a una clase/issue separado que consume el `UsageSnapshot` producido aquí.
- `AnthropicApiUsageDataSource` debe recibir `ITokenProvider` por constructor (inyección de dependencias), igual que el patrón ya usado en `CredentialsFileTokenProvider`/`ITokenProvider`.
- Nunca implementar refresco de OAuth propio ante 401/403; solo exponer un estado explícito de fallo para que el consumidor final muestre un aviso claro (regla de CLAUDE.md).
- Retry con backoff ante fallos transitorios es explícitamente alcance de F2, no de este issue.
- Nunca un token real en tests — usar siempre un `HttpMessageHandler` fake/stub, según el apartado QA del roadmap.
- Cobertura de test objetivo del proyecto: 70% (`testingCoverage` en `.claude/sdlc.config.yaml`); el test unitario de esta clase debe contribuir a ese objetivo para Infrastructure.

## Risks
- **Data quality:** Los headers `anthropic-ratelimit-unified-5h-*`/`-7d-*` no son un contrato oficial documentado por Anthropic (proceden de ingeniería inversa de la comunidad — ver Technical Notes); su nombre, presencia o formato exacto pueden cambiar sin aviso, o diferir de lo aquí documentado hasta que se complete la validación manual real que exige el Acceptance Criteria del issue original.
- **Cost/Quota:** No existe un endpoint de "solo estado" que no consuma cuota — cada llamada de `AnthropicApiUsageDataSource` (incluido cada ciclo de polling en fases posteriores como F1) consume una cantidad mínima de cuota real (`max_tokens: 1`). Este es un trade-off aceptado explícitamente por el usuario en esta fase, no un pendiente; debe tenerse en cuenta al definir la frecuencia de polling en F1.
- **Security:** El token OAuth se transmite en el header `Authorization`; debe evitarse registrar su valor en logs, mensajes de error o excepciones, tanto en éxito como en los distintos estados de fallo.
- **Performance:** N/A en esta fase (F0) — no hay polling periódico todavía; se valida con una llamada puntual/manual.
- **Compliance/Adoption:** Al depender de un comportamiento no documentado oficialmente y del header `User-Agent: claude-code/<versión>` para evitar un bucket de rate-limit más agresivo, existe el riesgo de que Anthropic cambie esta validación (p. ej. exigiendo un `User-Agent` más estricto, o bloqueando explícitamente clientes no oficiales) en el futuro, rompiendo la integración sin previo aviso.
- **Impact:** Medium — sin esta llamada funcionando, no hay datos reales de rate limit que mostrar (F1 dependería de datos simulados), pero el proyecto puede seguir avanzando en paralelo con otras piezas de F0 (p. ej. UI) usando datos simulados mientras se completa la validación manual contra la API real.
